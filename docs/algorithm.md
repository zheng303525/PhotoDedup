# 判重算法与阈值标定

本文记录「为什么这么判」和「阈值是怎么定出来的」，方便以后改算法时知道哪些数字不能拍脑袋动。

## 一、为什么必须分层

「是不是同一份文件」和「是不是同一张照片」是两个不同的问题：

- **同一份文件**：字节一致。零误判，可以据此清理。
- **同一张照片**：可能是缩放、重压缩、调色、水印、裁剪、旋转之后的版本。**必然有误判**，
  只能给候选。

混为一谈的后果很具体：如果拿感知哈希去判「哪份画质好」，它会把「看起来像」当成
「一样好」；如果拿 MD5 去找所有重复，微信转发的那一堆全抓不到。

所以顺序是固定的：**先能定论的定论掉，剩下交给感知层找候选，最后人工确认**。

## 二、四层判据

### 第 1 层：字节层

- 先按 `(文件大小)` 分桶，只有同桶内才算 MD5 —— 大小不同必然字节不同，可以省掉大部分 I/O
- 同桶内 MD5 相同 → `REL_EXACT`，**确定**

### 第 2 层：像素层

- 对「解码后哈希距离为 0 且尺寸相同但 MD5 不同」的候选，做整图解码 + RGB 逐字节比对
- 相同 → `REL_SAME_PIXEL`，**确定**（差异只在封装/元数据）
- 这一步必须全尺寸解码，代价高，所以只对极少数候选做

### 第 3 层：感知层

- **pHash**：32×32 灰度 → 正交 DCT-II → 取 8×8 低频 → 与中位数比较得 64 位
- **dHash**：9×8 灰度 → 水平梯度比较得 64 位
- **二面体变体**：各生成 8 种（旋转 0/90/180/270 + 水平镜像及其旋转），
  取两侧变体集合的最小汉明距离，解决「转过 90 度/镜像」的版本
- **候选生成用 MIH**：64 位切 4 段 16 位，利用「总距离 t ≤ 4k+3 时必有一段差异 ≤ k」
  只查段内距离 ≤ k 的桶。t=8 时 k=2，每段查 137 个掩码。
  一万张图的候选量从 5000 万降到百万级

### 第 4 层：几何层

- ORB（2000 特征点）+ BFMatcher（汉明，k=2，比率检验 0.75）→ RANSAC 单应性（阈值 5.0）
- 把 B 用单应矩阵变换到 A 的坐标系，统计差异分布：
  - **只在重叠区域内**做逐通道 z 分数归一化（去掉全局亮度/对比度变化）
  - 差异像素 = 三通道最大 |z 差| > 0.6
  - 形态学开运算去噪后做连通域分析，取最大块的面积占比与填充率
  - **统计「显著差异块数量」**（面积 > 重叠区 0.05% 的连通域个数）

判定组合：

| 条件 | 结论 |
|---|---|
| 差异分散、块数少（≤5）、最大块小 | `REL_NEAR`（较高） |
| **块数 ≥ 6 且最大块不大** —— 多处内容成片改动 | `REL_BURST`，**排除** |
| 差异集中在 1 块（>2.5% 或总差异 >4% 或填充率 >0.6） | `REL_BURST`，**排除** |
| 对齐后大面积不一致（>40%）且 pHash ≤ 2 | `REL_NEAR`，标注镜像/旋转，但置信只到「接近」 |
| 纹理太少 / 好匹配不足 | `REL_WEAK`，**排除** |
| 以上都不满足 | `REL_DIFF` |

**为什么要有「块数」这一条**：这是 928 张真实手机截图跑出来的教训。见下节。

## 三、实测数据（2026-11，800×600 合成样本，阈值 8）

### 正样本：同一张照片的不同版本

| 变体 | pHash | ORB 内点 | 结论 |
|---|---|---|---|
| 缩放 60% | 0 | 数百 | 成组 |
| 重压缩 Q35 | 0 | 数百 | 成组 |
| 亮度 +35% / 对比 0.85 | 2 | 185 | 成组 |
| 右下角水印 | 0 | 805 | 成组 |
| 旋转 90° | 0（变体命中） | 776 | 成组 |
| 水平镜像 | 0（变体命中） | 26 / 0.33 | 成组，但只给「接近」 |
| **中心裁掉 20%** | **24** | 287 | **抓不到**（见限制） |

### 负样本：长得像但不是同一张

| 样本 | pHash | ORB 内点 | 结论 | 是否正确 |
|---|---|---|---|---|
| **同场景连拍**（背景相同、物体挪位） | **4** | **880 / 0.981** | `REL_BURST` | ✅ 靠差异分布拦住 |
| 文档两页（文字不同） | 14 | 57 / 0.50 | 弱 | ✅ |
| 纯色墙两张 | 24 | 提不到点 | 不进候选 | ✅ |
| 棋盘格平移 | 22 | 0.02 | 不进候选 | ✅ |
| 同建筑不同角度 | 18 | 0.02 | 不进候选 | ✅ |

**连拍这一行是整套设计的原因**：pHash 4、内点率 0.98，前两道判据全过，
只有「差异集中在 2.86% 的连通块、填充率 0.79」这一条把它和真正的副本区分开。

### 真实库实测：928 张手机截图（2026-11-11）

合成样本过关之后，拿 `D:\OneDrive\Pictures\截图`（6629 个文件）实跑，
**第一次就撞出了合成样本没覆盖的假阳性**：多组「相隔几分钟的不同手机截图」
被判成同一张的不同版本，推荐直接删。

原因很清楚：手机截图的分辨率、状态栏、导航栏、布局全都一样，pHash 天然很近；
ORB 也能完美对齐（同一套 UI 元素）。而它们之间的差异是「文字换了」——
总差异 2.8%，但**最大连通块只有 0.14%**，所以躲过了「差异集中」这条判据。

于是补测了「显著差异块数量」这一维：

| 样本 | 真假 | 总差异 | 最大块 | 填充率 | **块数** | 旧判定 | 新判定 |
|---|---|---|---|---|---|---|---|
| 另存为 q60 | 真 | 0.00% | 0.00% | 0 | **0** | near ✅ | near ✅ |
| 缩到一半 | 真 | 0.03% | 0.00% | 1.00 | **0** | near ✅ | near ✅ |
| 角落小水印 | 真 | 0.00% | 0.00% | 0 | **0** | near ✅ | near ✅ |
| 调亮度+对比（高光溢出） | 真 | 7.54% | 7.22% | 0.95 | **4** | burst ❌漏 | burst（需人工） |
| 大块水印 | 真 | 8.92% | 5.26% | 1.00 | **4** | burst ❌漏 | burst（需人工） |
| **两张不同手机截图** | 假 | 2.81% | 0.14% | 0.92 | **8** | near ❌错 | **burst ✅拦住** |
| 两张极近截图（16 秒） | 假 | 0.02% | 0.01% | 0.79 | **0** | near | near（画面确实一样） |

结论：**真副本的块数恒为 0，内容改动是多个块**。所以判据加了
「块数 ≥ 6 且最大块不大 → 判为内容不同」。加了这条之后重跑，
6629 个文件 → 18 组、22 个副本，逐对看图核对全部成立。

代价是「大面积调色 / 大块水印」落进 burst 被排除（漏检），这符合
「宁可漏，不可错」的取舍。

## 四、阈值怎么调

| 参数 | 默认 | 含义 | 调大的后果 |
|---|---|---|---|
| `threshold` | 8 | 感知哈希允许的汉明距离 | 抓更多改动，假阳性上升 |
| `min_inliers` | 12 | RANSAC 内点下限 | 更严，漏更多 |
| `min_ratio` | 0.30 | 内点率下限 | 更严 |
| `max_block` | 0.025 | 最大差异连通块占比上限 | 更松，连拍更容易混进来 |
| `max_diff` | 0.04 | 总差异占比上限 | 同上 |
| `max_fill` | 0.6 | 差异块填充率上限 | 块越"实"越可疑，调小更严 |
| `max_blocks` | 6 | 显著差异块数量上限 | 调大能放过更多"多处改动"，误判风险上升 |
| `max_links` | 12 | 每张图最多连几个候选 | 调大更全面但更慢 |

调参方法：拿自己图库里**已知的**同图对和异图对做回归，
`scripts/diag_scan.py` 会把每对的判据数值都打出来，看正负样本的分界在哪。

## 五、为什么宁可漏不可错

用户的原话是「不怕没找到，就怕找错了」。这对工具设计有直接约束：

1. 感知层最高只给「较高」，措辞是「高度可能同一张」，永远不说「确定」
2. 得分接近时禁用 `Delete`，逼用户看图
3. 大幅裁剪这种「pHash 必失效」的场景，不做阈值妥协去硬抓 —— 调高阈值会成倍增加假阳性，
   而假阳性意味着用户得逐张排除，比漏掉更累
4. 连拍、纯色、扫描件这些几何层失效的场景，一律降级或排除，不猜

## 六、待改进

- **EXIF 时间交叉验证**：同一张的两个副本 `DateTimeOriginal` 相同，连拍通常差 1–2 秒。
  这是个很强的信号，但微信导出会改写时间戳，所以只能当加分项、不能当否决条件
- **裁剪检测**：可以尝试在 ORB 内点基础上估计裁剪边界，反推原始画面，再算一次哈希
- **同像素层的加速**：目前是整图全解码，可以改成「解码后对稀疏采样点逐字节比对」，
  牺牲极小的确定性换来数倍速度
